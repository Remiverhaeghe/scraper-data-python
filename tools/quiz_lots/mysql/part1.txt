@001
Q: Qu'est-ce que MariaDB par rapport à MySQL ?
C: Un fork libre de MySQL, largement compatible
W: Une interface graphique officielle pour administrer MySQL
W: L'ancien nom de MySQL avant son rachat par Oracle
W: Une extension de MySQL réservée au stockage de documents JSON
E: MariaDB est né en 2009 d'une partie de l'équipe d'origine de MySQL, après le rachat de Sun par Oracle. Les deux restent très proches pour le SQL courant et les outils, mais divergent sur certaines fonctions avancées. Beaucoup de distributions Linux installent MariaDB sous le nom de paquet mysql.

@002
Q: Quel moteur de stockage MySQL utilise-t-il par défaut, avec transactions et clés étrangères ?
C: InnoDB
W: MyISAM
W: MEMORY
W: CSV
E: InnoDB est le moteur par défaut depuis MySQL 5.5 : transactions, verrous par ligne, clés étrangères et reprise après plantage. MyISAM, l'ancien moteur, n'a ni transactions ni clés étrangères et verrouille la table entière. MEMORY garde les données en mémoire seulement.

@006

@012

@014

P: LEFT JOIN => toutes celles de gauche, NULL sans correspondance
P: RIGHT JOIN => toutes celles de droite, NULL sans correspondance
E: MySQL n'a pas de FULL OUTER JOIN : on l'obtient par un UNION entre un LEFT JOIN et un RIGHT JOIN. Un LEFT JOIN suivi de WHERE droite.id IS NULL trouve les lignes sans correspondance, comme les clients sans commande.

@015

@019
Q: Que fait INSERT ... ON DUPLICATE KEY UPDATE ?
C: Il insère la ligne ou met à jour celle qui existe déjà
W: Il insère la ligne en double sous un autre identifiant
W: Il refuse l'insertion et renvoie une erreur
W: Il supprime la ligne existante avant d'insérer
E: Si l'insertion viole une clé primaire ou unique, MySQL applique la clause UPDATE à la ligne existante. Pratique pour un compteur ou une synchronisation. REPLACE fait autrement : il supprime puis réinsère, ce qui déclenche les suppressions en cascade et change l'identifiant.
```sql
INSERT INTO stock (produit_id, quantite) VALUES (12, 5)

```

@020
Q: Qu'est-ce qu'une transaction ?
C: Des opérations validées ou annulées ensemble
W: Une requête lancée sur deux bases à la fois
W: Un journal des requêtes lentes du serveur
W: Une copie de la table prise avant chaque écriture
E: Entre START TRANSACTION et COMMIT, les modifications sont invisibles aux autres sessions puis validées d'un coup ; ROLLBACK les annule. En InnoDB, chaque instruction hors transaction explicite est validée aussitôt (autocommit). MyISAM ne gère pas les transactions du tout.

@021
Q: Que se passe-t-il si la connexion coupe entre ces deux UPDATE ?
C: Rien n'est validé, les deux soldes restent inchangés
W: Le premier compte est débité, le second n'est pas crédité
W: Les deux UPDATE sont rejoués à la reconnexion
W: La base est verrouillée jusqu'au redémarrage du serveur
E: Une transaction non validée est annulée quand la connexion se ferme. Le virement est tout ou rien, ce qui est le but. Sans transaction, en autocommit, le premier UPDATE serait validé seul et l'argent disparaîtrait.
```sql
START TRANSACTION;
UPDATE compte SET solde = solde - 100 WHERE id = 1;
UPDATE compte SET solde = solde + 100 WHERE id = 2;
COMMIT;
```

@022

@023

@027

@028

@031

@036

N: 15
E: En MySQL, DATEDIFF(fin, début) renvoie le nombre de jours, dans cet ordre-là : l'inverse de SQL Server, qui prend l'unité en premier. TIMESTAMPDIFF(MONTH, debut, fin) calcule dans d'autres unités. Confondre l'ordre donne un résultat négatif.

@043

U: Go
T: 3
E: 32 × 0,7 = 22,4 Go, en pratique 22 Go. Le reste sert au système, aux connexions et aux tampons de tri. Trop grand, le buffer pool pousse le système à utiliser le swap, ce qui est pire qu'un cache plus petit.

@048
Q: Pourquoi une colonne VARCHAR(255) en utf8mb4 indexée peut-elle poser problème sur une ancienne version ?
C: L'index dépasse la taille maximale d'une clé
W: utf8mb4 ne permet pas d'indexer du texte
W: VARCHAR ne peut pas dépasser 191 caractères
W: Les index sont limités à une colonne
E: utf8mb4 réserve jusqu'à 4 octets par caractère : 255 × 4 = 1 020 octets, au-delà de l'ancienne limite de 767 octets. D'où les VARCHAR(191) des vieux schémas. Le format de ligne DYNAMIC des versions récentes porte la limite à 3 072 octets.

@049
Q: Combien d'octets au plus réserve un VARCHAR(191) en utf8mb4 pour un index ?
N: 764
E: 191 × 4 = 764 octets, juste sous l'ancienne limite de 767. C'est l'origine de ce nombre étrange dans les migrations Laravel ou WordPress d'autrefois. Avec MySQL 5.7 et plus, le format DYNAMIC rend ce contournement inutile.

Q: Que fait la commande OPTIMIZE TABLE journal; sur une table InnoDB ?
C: Elle reconstruit la table pour récupérer l'espace libre
W: Elle crée automatiquement les index manquants
W: Elle réécrit les requêtes lentes qui lisent la table
W: Elle supprime les lignes en double de la table
E: Après la suppression de nombreuses lignes, le fichier de la table garde l'espace. OPTIMIZE TABLE la reconstruit et le rend au système. Sur une grande table, c'est long et lourd : on le planifie en heure creuse, ou on purge par partitions.

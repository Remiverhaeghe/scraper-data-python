W: Tous les dépôts GitHub publics peuvent assumer le rôle
W: Seuls les administrateurs AWS peuvent assumer le rôle depuis GitHub
W: Le rôle ne peut être assumé que le dimanche, jour de déploiement
E: La politique de confiance dit qui peut assumer le rôle. Le principal fédéré est le fournisseur OIDC de GitHub, et la condition sur le champ sub du jeton n'accepte que le dépôt acme/site sur la branche main. Sans cette condition, n'importe quel dépôt GitHub pourrait obtenir les droits du rôle.
```json
{
  "Effect": "Allow",
  "Principal": {"Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com"},
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:sub": "repo:acme/site:ref:refs/heads/main"
    }
  }
}
```

Q: Pourquoi des instances à processeur ARM (Graviton, Ampere, Cobalt) peuvent-elles réduire la facture d'une application Java ou Python ?
C: Elles offrent souvent un meilleur rapport performance-prix, sans changer le code
W: Elles ne sont facturées qu'à la moitié du temps d'utilisation réel
W: Elles exécutent le code sans système d'exploitation, donc plus vite
W: Elles sont réservées aux fonctions serverless, moins chères par nature
E: Les instances ARM coûtent en général moins cher que leurs équivalents x86 pour une performance comparable. Un code Java, Python ou Node.js tourne tel quel ; il faut seulement des images de conteneurs et des dépendances natives compilées pour ARM. On mesure sur sa charge réelle avant de basculer.

Q: Pourquoi une architecture multi-cloud n'est-elle pas automatiquement plus résiliente qu'une architecture sur un seul fournisseur bien répartie ?
C: Elle ajoute complexité et compétences sans garantie de gain
W: Parce que deux fournisseurs ne peuvent pas être joints par Internet
W: Parce que les données ne peuvent jamais être copiées entre fournisseurs
W: Parce qu'un seul fournisseur garantit 100 % de disponibilité
E: Plusieurs régions d'un même fournisseur couvrent déjà la plupart des pannes. Le multi-cloud double les outils, les réseaux, la sécurité et les compétences, et oblige à se limiter aux services communs. Il répond plutôt à des contraintes de négociation, de réglementation ou de dépendance à un fournisseur.

O: Tester l'application complète dans le cloud

N: 1100
U: $
T: 1

En contrepartie, une restauration prend jusqu'à douze heures et se paie au volume : ce choix convient à des sauvegardes de conformité qu'on espère ne jamais relire.

Q: Pourquoi des journaux applicatifs envoyés en masse vers un service géré (CloudWatch Logs, Log Analytics) peuvent-ils coûter plus cher que les serveurs eux-mêmes ?
C: L'ingestion se facture au gigaoctet, et le niveau DEBUG en produit énormément
W: Chaque ligne de journal ralentit le serveur et augmente sa taille
W: Les journaux sont copiés automatiquement dans toutes les régions
W: Le fournisseur facture chaque consultation d'une ligne de journal
E: Les services de journaux facturent surtout le volume ingéré puis stocké. Une application laissée en DEBUG en production, ou qui journalise chaque requête en entier, multiplie la facture. On fixe le bon niveau, on échantillonne et on limite la rétention, quitte à archiver ailleurs ce qui doit être gardé.

Q: Une instance privée n'arrive pas à joindre Internet malgré la passerelle NAT. La table de routage du sous-réseau privé contient ces routes. Quelle est la cause la plus probable ?
C: La route par défaut pointe vers la passerelle Internet au lieu de la passerelle NAT
W: La route locale 10.0.0.0/16 bloque le trafic sortant de l'instance
W: Une instance privée ne peut jamais utiliser de route par défaut
W: La passerelle NAT ne fonctionne qu'avec des adresses IPv6
E: Dans un sous-réseau privé, la route 0.0.0.0/0 doit viser la passerelle NAT. Vers une passerelle Internet, le trafic sort sans adresse publique et ne revient pas : l'instance reste coupée. La route locale permet seulement la communication à l'intérieur du VPC et ne gêne rien.
```
Destination      Cible
10.0.0.0/16      local
0.0.0.0/0        igw-0a1b2c3d
```

@097
Q: Pourquoi le trafic entre deux zones de disponibilité peut-il apparaître sur la facture d'une application très bavarde ?
C: Les données qui traversent les zones sont facturées au gigaoctet
W: Chaque zone facture l'électricité consommée par les autres zones
W: Le trafic entre zones passe toujours par Internet, donc par la NAT
W: Une même application ne peut pas être répartie sur plusieurs zones
E: Chez AWS notamment, le transfert entre zones d'une même région est facturé dans chaque sens. Des services qui s'appellent sans cesse entre zones, ou une réplication volumineuse, finissent par coûter. On garde la répartition entre zones pour la résilience, mais on surveille les flux et on évite les allers-retours inutiles.

@098
Q: Une fonction serverless appelée 3 millions de fois par mois dure 200 ms avec 512 Mo de mémoire. Combien de Go-secondes consomme-t-elle par mois ?
N: 300000
T: 1
E: Chaque appel consomme 0,5 Go × 0,2 s = 0,1 Go-seconde ; 3 millions d'appels donnent 300 000 Go-secondes. Au tarif d'environ 0,0000167 $ le Go-seconde, cela fait à peu près 5 $, plus le prix des requêtes. Réduire la mémoire ou la durée réduit la facture proportionnellement.

Q: Que fait ce rôle Kubernetes annoté sur EKS ?
C: Il associe le compte de service Kubernetes à un rôle IAM, pour des droits AWS par pod
W: Il donne au cluster entier les droits administrateur du compte AWS
W: Il crée un utilisateur IAM avec une clé d'accès pour chaque pod
W: Il ouvre le port 443 du cluster sur Internet pour les pods
E: Avec IRSA, ou EKS Pod Identity, les pods qui utilisent le compte de service facturation reçoivent les identifiants temporaires du rôle indiqué, et seulement eux.
```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: facturation
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::111122223333:role/facturation-s3
```

Q: Un service doit rester disponible même si une région entière tombe, avec un RPO de quelques secondes. Quelle base de données convient ?
C: Une base répliquée en continu vers une autre région
W: Une base RDS Multi-AZ, qui couvre aussi la perte de la région
W: Une sauvegarde quotidienne copiée dans une autre région
W: Un snapshot horaire du disque d'une base installée sur une VM
E: Multi-AZ protège d'une panne de zone, pas de région. Une sauvegarde quotidienne donne un RPO d'un jour, un snapshot horaire d'une heure. Une base globale réplique de façon continue vers une autre région avec un retard de l'ordre de la seconde, et permet d'y promouvoir la copie en écriture en cas de sinistre.

@001
Q: Une classe Facture calcule les totaux, génère le PDF et envoie le courriel au client. Quel principe enfreint-elle ?
C: La responsabilité unique : elle a trois raisons de changer
W: La substitution de Liskov, car elle ne peut pas être remplacée par une sous-classe
W: La ségrégation des interfaces, car elle n'implémente aucune interface du projet
W: L'ouverture-fermeture, car elle ne déclare pas de méthode abstraite à redéfinir
E: Un changement de mise en page du PDF, de règle de TVA ou de fournisseur de courriel touche la même classe. On sépare en CalculFacture, GenerateurPdf et EnvoiFacture, chacune testable seule.

@002
Q: Associer chaque principe SOLID à la situation qui le respecte.
P: Responsabilité unique => Le calcul de la TVA vit dans une classe à part
P: Ouvert-fermé => Un nouveau mode de paiement s'ajoute par une nouvelle classe
P: Substitution de Liskov => Toute sous-classe de Stockage s'utilise là où Stockage est attendu
P: Ségrégation des interfaces => Un lecteur dépend de Lecture, pas d'une interface qui écrit aussi
P: Inversion des dépendances => Le service métier dépend d'une interface, pas de la base PostgreSQL
E: Ces principes visent un code qui change sans casser ailleurs. Ils se lisent comme des signaux d'alerte, pas comme des règles à appliquer partout dès la première ligne.

@003
Q: Pourquoi ce code enfreint-il le principe ouvert-fermé ?
C: Chaque nouveau mode de paiement oblige à modifier cette méthode
W: La méthode est publique alors qu'elle devrait être déclarée privée
W: Le paramètre mode devrait être un entier plutôt qu'une chaîne
W: La méthode renvoie un nombre décimal au lieu d'un objet métier
E: Un switch sur un type qui revient dans plusieurs méthodes appelle le polymorphisme : une interface ModePaiement avec une implémentation par mode. Un switch unique et stable peut en revanche rester tel quel.
```java
double frais(String mode, double montant) {
    switch (mode) {
        case "carte": return montant * 0.015;
        case "virement": return 0.5;
        case "paypal": return montant * 0.029 + 0.35;
        default: throw new IllegalArgumentException(mode);
    }
}
```

@004
Q: Que dit le principe YAGNI (You Aren't Gonna Need It) ?
C: Ne pas coder une fonction tant qu'elle n'est pas réellement nécessaire
W: Ne pas réutiliser une fonction écrite par une autre équipe du projet
W: Ne pas écrire de test pour une fonction qui n'est pas encore appelée par le code
W: Ne pas documenter une fonction tant qu'elle n'est pas en production
E: Une abstraction prévue « pour plus tard » coûte du code à lire et à maintenir, et se révèle souvent mal adaptée au besoin réel. On simplifie aujourd'hui et on généralise quand le second cas arrive.

@005
Q: Que conseille le principe KISS ?
C: Préférer la solution la plus simple qui répond au besoin
W: Préférer la solution qui couvre le plus grand nombre de cas
W: Préférer la solution qui utilise le moins de lignes de code
W: Préférer la solution qui suit le plus de design patterns
E: Simple ne veut pas dire court : une boucle claire vaut mieux qu'une ligne astucieuse que personne ne relit. La complexité se justifie par un besoin, pas par l'élégance.

@006
Q: Pourquoi deux blocs de code identiques ne doivent-ils pas toujours être factorisés ?
C: S'ils changent pour des raisons différentes, la factorisation les lie à tort
W: Le compilateur optimise mieux deux blocs identiques qu'une fonction partagée
W: Une fonction partagée ne peut pas être testée séparément de ses appelants
W: Les règles de nommage interdisent deux fonctions qui font la même chose
E: Le calcul des frais de port et celui d'une pénalité peuvent coïncider aujourd'hui et diverger demain. Une mauvaise abstraction se remplit de paramètres et de conditions : mieux vaut un peu de duplication qu'un mauvais regroupement.

@007
Q: Qu'est-ce qu'un nom de fonction révélateur d'intention ?
C: Un nom qui dit ce que fait la fonction, comme calculerTotalTtc
W: Un nom court qui tient en trois lettres, comme ctt ou clc
W: Un nom qui reprend le type de retour, comme doubleResultat
W: Un nom qui reprend le numéro du ticket, comme fonctionJira482 ou correctifTicket17
E: Le lecteur comprend l'appel sans ouvrir la fonction. Un nom difficile à trouver signale souvent une fonction qui fait plusieurs choses.

@008

C: Qu'elle fait deux choses différentes selon la valeur, peu lisibles à l'appel
W: Qu'elle ne peut être appelée que depuis une méthode de test unitaire du module
W: Qu'elle s'exécute deux fois plus vite qu'une fonction sans paramètre
W: Qu'elle doit être déclarée statique pour fonctionner correctement
E: À l'appel, true ne dit rien. Deux fonctions, envoyerParCourriel et envoyerParCourrier, ou un paramètre de type énuméré, rendent l'intention visible.

@009
Q: Qu'est-ce qu'un effet de bord dans une fonction ?
C: Une modification de l'état extérieur, comme écrire en base ou changer un champ
W: Une erreur levée quand un paramètre reçu par la fonction appelée est jugé invalide
W: Une valeur de retour différente selon le type du paramètre reçu
W: Un appel récursif de la fonction à elle-même sans condition d'arrêt
E: Une fonction pure, sans effet de bord, renvoie toujours le même résultat pour les mêmes entrées : elle se teste et se réutilise facilement. On regroupe les effets de bord aux bords du programme.

@010
Q: Pourquoi préférer la composition à l'héritage pour réutiliser du code ?
C: La composition assemble des comportements sans lier la classe à toute une hiérarchie
W: L'héritage n'est pas pris en charge par les langages orientés objet les plus récents
W: La composition s'exécute plus vite que l'appel d'une méthode héritée
W: L'héritage interdit d'écrire des tests unitaires pour les sous-classes
E: Une sous-classe dépend des détails de sa classe parente : un changement dans le parent peut la casser. Une classe qui contient un Notificateur peut en changer, même à l'exécution.

@015

C: À faire fonctionner une classe avec une interface qu'elle n'implémente pas
W: À créer des objets complexes étape par étape avec des valeurs fixées par défaut
W: À limiter l'application à une seule instance d'une classe donnée
W: À notifier plusieurs objets lorsqu'un objet change d'état
E: Un service de courriel tiers expose envoyerMessage(dest, corps) ; l'adaptateur implémente l'interface Notificateur du projet et traduit les appels. Changer de fournisseur ne touche que l'adaptateur.

@018
Q: Qu'est-ce que la cohésion d'une classe ?
C: La force du lien entre ses éléments, qui servent un même but
W: Le nombre de classes qui dépendent d'elle dans le projet
W: Le nombre de lignes de code qu'elle contient au total
W: La part de ses méthodes couvertes par des tests unitaires automatisés
E: Une classe cohésive a des méthodes qui utilisent les mêmes données pour un même rôle. Une classe Utilitaires qui regroupe dates, fichiers et TVA a une cohésion faible.

@019
Q: Que signifie un couplage fort entre deux classes ?
C: Modifier l'une oblige souvent à modifier l'autre
W: Les deux classes s'exécutent toujours dans le même thread
W: Les deux classes sont rangées dans le même fichier source
W: Les deux classes partagent une même classe parente
E: On vise une forte cohésion et un faible couplage : des modules qui font une chose et dépendent peu des détails des autres. Dépendre d'une interface plutôt que d'une classe concrète réduit le couplage.

W: Ne pas appeler une méthode statique depuis une méthode d'instance

@031

@034

Q: Qu'est-ce que la dette technique ?
C: Le coût futur des raccourcis pris aujourd'hui dans le code ou l'architecture
W: Le budget à rembourser au fournisseur d'une licence logicielle arrivée à expiration
W: Le temps passé à former les nouveaux développeurs sur le projet
W: La somme des bogues signalés par les utilisateurs non encore corrigés
E: Comme une dette financière, elle peut être un choix raisonnable pour livrer vite, à condition d'être connue et remboursée. Ses intérêts se paient en lenteur de chaque évolution.

@046
Q: Pourquoi noter une décision d'architecture dans un ADR (Architecture Decision Record) ?
C: Pour garder le contexte, les options étudiées et la raison du choix
W: Pour obtenir la validation automatique de la décision par la CI
W: Pour générer le diagramme d'architecture à partir de la décision prise
W: Pour empêcher toute modification de la décision par l'équipe
E: Deux ans plus tard, « pourquoi RabbitMQ et pas Kafka ? » trouve sa réponse dans le dépôt. Un ADR remplacé n'est pas effacé : un nouvel ADR le marque comme dépassé.

@047
Q: Associer chaque défaut de code à sa correction habituelle.
P: Méthode trop longue => Extraire des méthodes bien nommées
P: Switch sur un type répété => Remplacer par du polymorphisme
P: Longue liste de paramètres => Regrouper dans un objet paramètre
P: Nombre magique => Le remplacer par une constante nommée
P: Code mort => Le supprimer, l'historique Git le garde
E: Ces corrections sont décrites dans le catalogue de refactoring de Martin Fowler. Les IDE en automatisent beaucoup, ce qui limite le risque d'erreur.

@048
Q: Que dit la loi de Conway ?
C: L'architecture d'un système reflète la structure de communication de l'équipe qui le construit
W: La complexité d'un logiciel double tous les deux ans sans effort de simplification
W: Un projet en retard prend encore plus de retard quand on lui ajoute des personnes
W: Le temps de travail s'étend pour remplir la durée disponible jusqu'à l'échéance
E: Trois équipes qui se parlent peu produisent trois modules faiblement intégrés. On peut s'en servir à l'envers : organiser les équipes selon l'architecture souhaitée.

@049
Q: Quel est le premier niveau du modèle C4 pour décrire une architecture ?
C: Le contexte : le système, ses utilisateurs et les systèmes avec lesquels il échange
W: Le code : les classes et leurs relations dans chaque module du système
W: Les conteneurs : les applications, bases et files qui composent le système étudié ici
W: Les composants : les grands blocs à l'intérieur de chaque application
E: Contexte, conteneurs, composants, code : on zoome du plus large au plus fin. Le niveau contexte se montre à un non-technicien ; le niveau code se génère souvent à partir des sources.

Q: Des adresses électroniques apparaissent dans des attributs de spans. Où les retirer en premier, sans attendre une correction de chaque application ?
C: Dans un processor du collecteur qui masque ou supprime ces attributs
W: Dans Grafana, en masquant la colonne lors de l'affichage
W: Dans le stockage des traces, en réduisant la durée de conservation à un jour
W: Dans Alertmanager, en filtrant les alertes concernées
E: Le collecteur est le point de passage commun : un processor attributes, redaction ou transform y retire la donnée avant tout stockage. La correction dans le code reste nécessaire, mais le risque RGPD est stoppé tout de suite.

@096
Q: Un service interne ne reçoit que quelques requêtes par heure. Pourquoi un SLO basé sur la part de requêtes réussies y est-il trompeur ?
C: Deux échecs sur dix requêtes font chuter le ratio et déclenchent l'alerte
W: Prometheus ne collecte pas les services qui reçoivent peu de requêtes par heure
W: Le budget d'erreur ne se calcule que sur un trafic continu
W: Les requêtes rares ne sont pas comptées par les counters
E: Avec peu d'événements, le ratio varie fortement. On allonge la fenêtre, on ajoute du trafic synthétique ou on passe à un SLO par tranches de temps (minutes bonnes ou mauvaises).

@097
Q: Quel avantage offre une instrumentation par eBPF, comme Grafana Beyla ?
C: Elle mesure les appels HTTP et SQL sans modifier ni redémarrer l'application
W: Elle remplace les journaux applicatifs par des traces complètes
W: Elle fonctionne sur Windows comme sur Linux sans configuration
W: Elle donne le détail des fonctions métier appelées dans le code de l'application
E: eBPF observe les appels système et réseau depuis le noyau Linux : une application ancienne obtient des métriques RED et des traces de base. Pour le détail du code métier, une instrumentation par SDK reste nécessaire.

@098

@099
Q: Remettre dans l'ordre la mise en place d'un SLO pour un service.
O: Choisir le parcours utilisateur qui compte le plus
O: Définir le SLI qui mesure ce parcours
O: Fixer l'objectif et la fenêtre, par exemple 99,5 % sur 28 jours
O: Poser les alertes de consommation du budget d'erreur
O: Revoir l'objectif après quelques semaines de mesures réelles
E: Partir des métriques disponibles plutôt que du besoin de l'utilisateur donne des SLO sans intérêt. Un objectif fixé trop haut sans historique déclenche des alertes permanentes ; on l'ajuste après observation.

@100
Q: Que prévoit une politique de budget d'erreur quand le budget du mois est épuisé ?
C: Les mises en production de fonctions sont gelées au profit de la fiabilité
W: Le SLO est abaissé pour que le budget redevienne positif
W: Les alertes du service sont coupées jusqu'au mois suivant
W: L'équipe d'exploitation reprend la maintenance du code de l'équipe de développement
E: La politique, signée à l'avance par le produit et la technique, évite le débat pendant la crise. Les correctifs de fiabilité et de sécurité continuent de partir ; le gel cesse quand le budget se reconstitue.

@001
Q: Pourquoi utiliser uint16_t plutôt que unsigned int dans un code embarqué ?
C: Sa taille est fixée à 16 bits quel que soit le compilateur
W: Il est plus rapide à calculer que unsigned int sur tous les processeurs 32 bits
W: Il est rangé en mémoire flash et ne consomme donc pas de mémoire vive
W: Il interdit au compilateur toute optimisation sur la variable déclarée
E: La taille de int dépend de la cible : 16 bits sur un AVR, 32 bits sur un Cortex-M. Les types de stdint.h (uint8_t, int32_t…) rendent explicite la taille d'un registre ou d'une trame et évitent les surprises au portage.

@002
Q: Combien d'octets occupe un int sur un ATmega328P (Arduino Uno) avec avr-gcc ?
N: 2
U: octets
E: Sur AVR, int fait 16 bits : un compteur int dépasse 32 767 et devient négatif. C'est une erreur fréquente en reprenant un code écrit pour un PC ou un Cortex-M, où int fait 32 bits.

@003
Q: Que fait le mot-clé volatile sur cette variable ?
C: Il force une relecture en mémoire à chaque accès, sans mise en cache dans un registre
W: Il rend les accès à la variable atomiques entre l'interruption et la boucle
W: Il place la variable dans une zone de mémoire protégée contre l'écriture
W: Il remet la variable à zéro à chaque redémarrage du microcontrôleur
E: Sans volatile, le compilateur peut lire flag une seule fois et boucler indéfiniment, car rien dans la boucle ne le modifie. volatile ne protège pas d'un accès concurrent : il garantit seulement que chaque lecture va en mémoire.
```c
volatile bool flag = false;

void EXTI0_IRQHandler(void) { flag = true; }

int main(void) {
    while (!flag) { }
}
```

@004
Q: Compléter cette ligne qui met à 1 le bit 5 du registre PORTB sans toucher aux autres.
A: |=
E: Le OU bit à bit avec un masque n'allume que le bit voulu. Une affectation simple PORTB = (1 << 5) éteindrait les sept autres sorties du port, une erreur classique.
```c
PORTB ____ (1 << 5);
```

@005
Q: Compléter cette ligne qui met à 0 le bit 3 du registre PORTB.
A: ~
E: On inverse le masque pour obtenir des 1 partout sauf sur le bit 3, puis on applique un ET. Le OU exclusif, ^=, inverse le bit au lieu de le forcer à 0.
```c
PORTB &= ____(1 << 3);
```

@006
Q: Associer chaque opération sur le bit n d'un registre REG à son écriture en C.
P: Mettre à 1 => REG |= (1u << n)
P: Mettre à 0 => REG &= ~(1u << n)
P: Inverser => REG ^= (1u << n)
P: Tester => (REG >> n) & 1u
E: Ces quatre écritures reviennent dans tout pilote bas niveau. Le suffixe u rend le masque non signé : 1 << 31 sur un int signé est un comportement indéfini en C.

@007
Q: Une variable uint8_t vaut 250. Quelle valeur contient-elle après lui avoir ajouté 10 ?
N: 4
E: Un uint8_t va de 0 à 255 : 260 modulo 256 donne 4. Le débordement d'un entier non signé est défini en C, celui d'un entier signé ne l'est pas : le compilateur peut alors supposer qu'il n'arrive pas.

@011

@012
Q: Quelle différence entre une macro #define et une constante const en C ?
C: La macro est un remplacement de texte, la constante a un type vérifié
W: La macro est stockée en mémoire vive, la constante dans la mémoire flash

W: La macro est visible dans le débogueur, la constante ne l'est pas
E: Le préprocesseur remplace le texte avant la compilation, sans contrôle de type ni de portée. Une macro mal parenthésée, comme #define DOUBLE(x) x * 2, donne un résultat faux pour DOUBLE(a + 1).

@013
Q: Que vaut l'expression CARRE(2 + 1) avec cette macro ?
N: 5
E: Le préprocesseur écrit 2 + 1 * 2 + 1, soit 5 et non 9. On parenthèse chaque paramètre et l'expression entière : #define CARRE(x) ((x) * (x)). En C++, une fonction constexpr évite le problème.
```c
#define CARRE(x) x * x
```

@014

W: Attendre que le système d'exploitation charge le programme suivant en mémoire

W: Empêcher le chien de garde de redémarrer le microcontrôleur trop tôt
E: Sur un PC, main rend la main au système. En embarqué, sortir de main mène à un comportement dépendant du code de démarrage, souvent une boucle vide ou un redémarrage. La super-boucle lit les entrées, traite, écrit les sorties, puis recommence.

@016

@017
Q: Une liaison UART à 115 200 bauds utilise le format 8N1 (1 bit de départ, 8 de données, 1 d'arrêt). Combien d'octets peut-elle transmettre par seconde au maximum ?
N: 11520
U: octets/s
E: Chaque octet coûte 10 bits sur la ligne : 115 200 / 10 = 11 520 octets par seconde. Un journal de débogage trop bavard sur l'UART peut ainsi ralentir toute la boucle si l'envoi est bloquant.

@018

C: Un débit ou un format de trame différent de part et d'autre
W: Un câble trop court entre les deux broches TX et RX des cartes
W: Une adresse d'esclave mal réglée sur la carte qui reçoit les données
W: Une résistance de terminaison de 120 Ω absente en bout de ligne
E: Les deux côtés doivent avoir le même débit, le même nombre de bits, de parité et de bits d'arrêt, ainsi qu'une masse commune. On vérifie aussi que TX d'un côté va bien sur RX de l'autre.

@019
Q: Pourquoi les lignes SDA et SCL d'un bus I2C ont-elles besoin de résistances de rappel ?
C: Les composants ne font que tirer la ligne à 0, la résistance la ramène à 1
W: Les résistances limitent le courant de court-circuit entre deux esclaves
W: Les résistances filtrent les parasites venant de l'alimentation de la carte
W: Les résistances fixent l'adresse de chaque esclave relié au bus I2C
E: Les sorties I2C sont à drain ouvert : plusieurs composants peuvent tirer la ligne sans conflit. Des valeurs de 2,2 à 10 kΩ sont courantes ; trop fortes, les fronts montants deviennent lents et le bus échoue à 400 kHz.

@022

@023

N: 10
E: sizeof(tab) vaut 20 octets (10 éléments de 2 octets), divisé par la taille d'un élément. Le calcul ne fonctionne plus une fois le tableau passé à une fonction : il devient un pointeur et sizeof renvoie la taille d'une adresse.
```c
uint16_t tab[10];
```

@028

@029

N: 250
E: 16 MHz / 64 = 250 kHz, soit un tick toutes les 4 µs ; 1 ms / 4 µs = 250. Sur un temporisateur qui compte de 0 à la valeur de comparaison, on charge souvent 249, car le zéro compte aussi.

@030

U: mV
T: 1

@034

@040

E: Le délai entre l'événement et le traitement reste borné, quelle que soit la charge des tâches moins prioritaires. C'est ce qu'apporte un RTOS par rapport à une super-boucle, où l'événement attend la fin du tour.

@046
Q: Une tâche basse prend un mutex, une tâche haute l'attend, et une tâche moyenne occupe le processeur. Comment s'appelle ce problème ?
C: L'inversion de priorité
W: L'interblocage entre tâches
W: La famine de la tâche basse
W: Le débordement de la pile
E: La tâche haute attend en réalité la tâche moyenne, qui empêche la basse de rendre le mutex. L'héritage de priorité élève temporairement la tâche basse ; c'est la panne célèbre de Mars Pathfinder en 1997.

@047
Q: Deux tâches prennent les mutex A et B dans un ordre différent et restent bloquées. Quelle règle évite ce blocage ?
C: Prendre les mutex dans le même ordre dans toutes les tâches
W: Donner aux deux tâches exactement la même priorité de départ
W: Remplacer les mutex par des sémaphores binaires équivalents
W: Augmenter la taille de la pile de chacune des deux tâches
E: L'interblocage demande une attente circulaire : la tâche 1 tient A et attend B, la tâche 2 tient B et attend A. Un ordre fixe supprime le cycle ; un délai d'attente sur la prise du mutex permet aussi de détecter le problème.

@048
Q: Comment détecter un débordement de pile d'une tâche FreeRTOS ?
C: Activer configCHECK_FOR_STACK_OVERFLOW et suivre uxTaskGetStackHighWaterMark
W: Lire la valeur de retour de xTaskCreate à chaque tour de boucle de la tâche
W: Compiler avec l'option -O0 pour que le compilateur ajoute des contrôles
W: Désactiver les interruptions pendant les fonctions qui utilisent la pile
E: Le noyau remplit la pile d'un motif connu et vérifie qu'il n'est pas écrasé ; le crochet vApplicationStackOverflowHook est alors appelé. La marge mesurée en essai sert à dimensionner chaque pile au plus juste.

@049
Q: Pourquoi utiliser une file de messages plutôt qu'une variable globale entre deux tâches ?
C: La file copie les données et réveille la tâche qui attend
W: La file range les données en flash pour les garder après coupure
W: La file accélère l'exécution en évitant les appels au noyau
W: La file supprime le besoin d'attribuer une priorité aux tâches
E: La variable globale demande une protection et une scrutation ; la file assure la cohérence de chaque message et bloque la tâche lectrice tant qu'elle est vide. Les messages sont copiés : on y place une petite structure ou un pointeur vers un tampon.

@050
Q: Pourquoi désactive-t-on souvent les exceptions C++ (-fno-exceptions) sur un microcontrôleur ?
C: Elles ajoutent du code et un temps de traitement difficile à borner
W: Les compilateurs ARM ne savent pas les générer pour les cœurs Cortex-M
W: Elles imposent l'usage d'un système d'exploitation comme Linux
W: Elles empêchent l'utilisation des classes et des constructeurs
E: Le déroulement de la pile demande des tables et une bibliothèque de support, coûteux en flash, avec une durée variable. On renvoie alors des codes d'erreur, std::optional ou std::expected (C++23), et on désactive aussi souvent RTTI.

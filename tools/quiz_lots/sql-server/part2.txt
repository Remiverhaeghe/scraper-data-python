@051
Q: Que renvoie cette requête ?

E: ROW_NUMBER numérote les commandes de chaque client (PARTITION BY) de la plus récente à la plus ancienne ; on garde le numéro 1. La CTE est nécessaire car une fonction de fenêtrage ne s'utilise pas directement dans le WHERE.
```sql
WITH Classees AS (

```

@053
Q: Que calcule cette fonction de fenêtrage ?
C: Le cumul des ventes de chaque mois depuis le début de l'année
W: La moyenne des ventes sur toute l'année, répétée sur chaque ligne
W: Les ventes du mois précédent, pour comparaison
W: Le rang de chaque mois selon le montant des ventes
E: SUM ... OVER (ORDER BY Mois) additionne les lignes de la première jusqu'à la ligne courante : c'est un total cumulé. Préciser ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW évite le cadre RANGE par défaut, plus lent. LAG(Ventes) donnerait le mois précédent.
```sql
SELECT Mois, Ventes,
       SUM(Ventes) OVER (ORDER BY Mois
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS Cumul
FROM VentesMensuelles;

@056
Q: Que produit cette CTE récursive sur une table d'employés ?
C: La chaîne hiérarchique sous le directeur, avec le niveau de chacun
W: La liste des directeurs, sans leurs subordonnés
W: Une boucle infinie, la récursivité étant interdite en T-SQL
W: Le nombre d'employés de chaque service
E: Le premier SELECT, l'ancre, part du directeur sans responsable ; le second rejoint les employés dont le responsable est déjà trouvé, niveau après niveau. La récursion s'arrête quand plus aucune ligne n'est ajoutée, ou à 100 niveaux par défaut (MAXRECURSION).
```sql
WITH Hierarchie AS (
    SELECT Id, Nom, 0 AS Niveau FROM Employe WHERE ResponsableId IS NULL
    UNION ALL
    SELECT e.Id, e.Nom, h.Niveau + 1
    FROM Employe e JOIN Hierarchie h ON e.ResponsableId = h.Id
)
SELECT * FROM Hierarchie;
```

@059
Q: Qu'est-ce qu'un interblocage (deadlock) ?
C: Deux transactions qui attendent chacune un verrou tenu par l'autre
W: Une requête bloquée par un disque plein pendant l'écriture
W: Un utilisateur qui ne peut plus se connecter faute de licence
W: Une table qui ne peut plus recevoir d'insertion
E: A verrouille la table 1 puis demande la 2, B verrouille la 2 puis demande la 1 : aucune ne peut avancer. Accéder aux tables toujours dans le même ordre et garder les transactions courtes réduit le risque.

@072

```sql

END;

La procédure appelante reçoit alors une erreur de compteur incohérent. On teste @@TRANCOUNT et on utilise des points de sauvegarde (SAVE TRANSACTION) si besoin.

@093
Q: Que permet un point de sauvegarde (SAVE TRANSACTION) ?
C: Annuler une partie de la transaction sans annuler le reste
W: Sauvegarder la base pendant une transaction en cours
W: Valider la transaction en deux fois pour aller plus vite
W: Reprendre une transaction après un redémarrage du serveur
E: SAVE TRANSACTION Etape1 marque un point ; ROLLBACK TRANSACTION Etape1 annule ce qui suit sans toucher à ce qui précède, et la transaction continue. Utile pour une procédure qui tente une étape facultative. Un ROLLBACK sans nom annule toujours tout.

@094
Q: Une table de 120 millions de lignes doit être purgée des données de plus de 5 ans. Pourquoi supprimer par lots ?
C: Pour éviter un journal énorme et de longs blocages
W: Parce que DELETE ne peut pas traiter plus d'un million de lignes
W: Pour que les lignes supprimées restent récupérables
W: Parce que les index interdisent les suppressions massives
E: Un seul DELETE de 50 millions de lignes remplit le journal de transactions, verrouille longtemps la table et, s'il échoue, met aussi longtemps à s'annuler. Une boucle DELETE TOP (10000) ... jusqu'à @@ROWCOUNT = 0 garde des transactions courtes. Le partitionnement permet même d'éliminer une partition entière instantanément.

@095
Q: Combien de lots de 10 000 lignes faut-il pour supprimer 2,5 millions de lignes ?
N: 250
E: 2 500 000 / 10 000 = 250 lots. Chaque lot est une transaction courte : les autres utilisateurs peuvent travailler entre deux, et en mode FULL, une sauvegarde du journal pendant la purge évite qu'il grossisse trop. On ajoute parfois une courte pause entre les lots.

@096
Q: À quoi sert le partitionnement d'une table de commandes par année ?
C: Gérer chaque année à part et lire moins
W: Répartir la table entre plusieurs serveurs différents
W: Chiffrer chaque année avec une clé différente
W: Dupliquer les commandes pour accélérer les lectures
E: Une fonction et un schéma de partition rangent les lignes par année. Une requête filtrée sur une année ne lit que sa partition ; archiver une année se fait par SWITCH, instantané, au lieu d'un DELETE massif. Ce n'est pas un remède universel : mal choisi, il peut ralentir des requêtes.

@097
Q: Pourquoi éviter SELECT * dans le code d'une application ?
C: Il lit trop et casse quand la table change
W: Il est interdit dans les procédures stockées
W: Il ne renvoie que la première colonne de la table
W: Il verrouille la table entière pendant la lecture
E: SELECT * transporte des colonnes dont on n'a pas besoin, parfois volumineuses, et empêche un index couvrant de servir. L'ajout d'une colonne change le résultat et peut casser un code qui lit par position. On liste les colonnes utiles, ce qui documente aussi l'intention.

@098
Q: Que vaut @@TRANCOUNT après deux BEGIN TRANSACTION successifs sans COMMIT ?
N: 2
E: Chaque BEGIN TRANSACTION incrémente @@TRANCOUNT, chaque COMMIT le décrémente ; seul le COMMIT qui le ramène à 0 valide réellement. Un ROLLBACK le remet à 0 d'un coup. Vérifier IF @@TRANCOUNT > 0 avant un ROLLBACK évite une erreur quand rien n'est ouvert.

@099
Q: Associer chaque niveau d'isolation au phénomène qu'il autorise encore.
P: READ UNCOMMITTED => lectures de données non validées
P: READ COMMITTED => une relecture peut voir une valeur changée
P: REPEATABLE READ => de nouvelles lignes peuvent apparaître
P: SERIALIZABLE => aucun des trois
E: Plus le niveau est strict, plus les verrous durent et plus la concurrence baisse. READ COMMITTED est le niveau par défaut. SNAPSHOT offre une vue cohérente de toute la transaction sans bloquer les écrivains, grâce aux versions de lignes dans tempdb.

@100
Q: Pourquoi tester régulièrement la restauration des sauvegardes sur un autre serveur ?
C: Pour prouver qu'elles servent et chronométrer la reprise
W: Parce qu'une sauvegarde non restaurée expire au bout d'un mois
W: Pour libérer de la place sur le serveur de production
W: Parce que SQL Server l'exige pour accepter la sauvegarde suivante
E: Une sauvegarde peut être corrompue, incomplète ou dépendre d'un certificat perdu, comme avec TDE. Seule une restauration réelle le révèle, et elle donne le temps de reprise effectif à comparer au RTO promis. On y lance aussi DBCC CHECKDB, sans charger la production.

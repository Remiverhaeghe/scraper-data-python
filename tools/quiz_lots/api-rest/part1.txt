@001
Q: Que désigne une ressource dans une API REST ?
C: Une entité exposée par l'API et identifiée par une URI, comme /clients/42
W: Une méthode Java annotée qui traite une requête
W: Le serveur physique qui héberge l'API
W: Un fichier de configuration YAML chargé au démarrage du service web par le framework
E: REST raisonne en ressources (un client, une commande, la liste des commandes) que l'on manipule avec les méthodes HTTP. L'URI désigne la ressource, la méthode dit ce qu'on en fait : GET /clients/42 lit, DELETE /clients/42 supprime.

@002
Q: Associer chaque méthode HTTP à son usage dans une API REST.
P: GET => Lire une ressource ou une collection
P: POST => Créer une ressource dans une collection
P: PUT => Remplacer entièrement une ressource
P: PATCH => Modifier une partie d'une ressource
P: DELETE => Supprimer une ressource
E: Ce découpage permet de comprendre une route sans lire son code. Une API qui fait tout passer en POST (POST /getClient, POST /deleteClient) perd ce sens et le bénéfice des caches, des relances automatiques et des outils qui s'appuient sur la méthode.

@003
Q: Associer chaque famille de codes de statut HTTP à sa signification.
P: 2xx => Succès
P: 3xx => Redirection
P: 4xx => Erreur du client
P: 5xx => Erreur du serveur
E: Le premier chiffre suffit souvent au diagnostic : un 4xx demande de corriger la requête (paramètre, droits, format), un 5xx oriente vers les journaux du serveur. Un client ne relance automatiquement que sur certains 5xx et sur 429, jamais sur un 400.

@004
Q: Une création de commande par POST /commandes réussit. Quel code de statut répondre ?
C: 201 Created
W: 200 OK avec un corps vide
W: 202 Accepted, systématiquement, puisque l'écriture en base prend toujours un peu de temps
W: 204 No Content
E: 201 indique qu'une ressource a été créée ; la réponse porte l'en-tête Location vers son URI et souvent sa représentation. 202 est réservé à un traitement réellement différé, dont le résultat n'existe pas encore au moment de la réponse.

@005
Q: Quelle est la différence entre les codes 401 et 403 ?
C: 401 : identité absente ou invalide ; 403 : client identifié mais non autorisé
W: 401 : client identifié mais non autorisé ; 403 : jeton absent
W: 401 signale une ressource inexistante et 403 une méthode que la route n'accepte pas du tout
W: Aucune, les deux codes sont interchangeables
E: Malgré son nom (Unauthorized), 401 concerne l'authentification : il faut se connecter ou renouveler le jeton, et la réponse porte WWW-Authenticate. 403 dit que la personne est connue mais n'a pas le droit : se reconnecter n'y changera rien.

@006

@007
Q: Que signifie qu'une API REST est sans état (stateless) ?
C: Chaque requête porte tout ce qu'il faut pour être traitée, sans session côté serveur
W: L'API ne stocke aucune donnée en base
W: Les réponses ne contiennent jamais de code de statut
W: Le serveur ignore les en-têtes envoyés par le client et ne lit que le corps de la requête
E: Le jeton d'authentification, les paramètres et le corps voyagent avec chaque requête. N'importe quelle instance derrière le répartiteur de charge peut alors répondre, ce qui facilite la montée en charge et les redémarrages. Les données métier, elles, restent bien en base.

@008
Q: Que fait cette commande curl ?

W: Elle lit la fiche du client Durand

E: -X POST fixe la méthode, -H ajoute un en-tête et -d fournit le corps. Content-Type annonce au serveur comment lire ce corps : sans lui, curl envoie application/x-www-form-urlencoded et beaucoup d'API répondent 415 ou 422.
```bash
curl -X POST https://api.exemple.fr/clients \
  -H "Content-Type: application/json" \

```

@026
Q: Quelle méthode HTTP n'est pas idempotente ?
C: POST
W: PUT
W: DELETE
W: GET
E: Une méthode idempotente produit le même effet sur le serveur qu'on l'envoie une fois ou dix. Après un délai dépassé, on peut relancer un PUT ou un DELETE sans crainte ; relancer un POST peut créer une deuxième commande.

@027

P: GET => Sûre et idempotente
P: DELETE => Idempotente mais modifie l'état
P: POST => Ni sûre ni idempotente
P: OPTIONS => Sûre, décrit les possibilités de la route
E: Ces propriétés sont un contrat : les clients HTTP, proxys et passerelles s'en servent pour décider s'ils peuvent relancer seuls. Un DELETE rejoué sur une ressource déjà supprimée renvoie souvent 404, mais l'état du serveur est bien le même.

@034
Q: Que faut-il corriger dans cette boucle de relance d'un client Python ?
C: Elle relance aussitôt, sans lire Retry-After ni limiter les essais
W: timeout=10 est interdit avec requests
W: Le code 429 n'est jamais renvoyé par une API
W: Il faut remplacer get par post pour que le serveur accepte une deuxième tentative
E: Cette boucle martèle le serveur qui demande justement de ralentir. On attend la durée de Retry-After, sinon une attente exponentielle avec aléa, on plafonne le nombre d'essais et on journalise l'abandon.
```python
while True:
    vResponse = requests.get(vUrl, timeout=10)
    if vResponse.status_code != 429:
        break
```

@037

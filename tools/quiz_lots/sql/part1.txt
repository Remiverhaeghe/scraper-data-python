@001
Q: Compléter cette requête qui trie les clients par ville, puis par nom.
A: ORDER BY
E: Sans ORDER BY, l'ordre des lignes n'est pas garanti, même s'il semble stable en test. Chaque colonne peut avoir son sens : ORDER BY ville ASC, nom DESC.
```sql
SELECT nom, ville FROM client
____ ville, nom;
```

@002
Q: Que renvoie cette requête ?
C: Le nombre de commandes de chaque client, pour les clients ayant commandé
W: Le nombre total de commandes, répété sur chaque ligne de la table client
W: Le nombre de clients différents ayant passé au moins une commande
W: La liste des commandes triées par client, sans regroupement
E: Chaque groupe correspond à un client_id présent dans commande. Les clients sans commande n'apparaissent pas : il faudrait partir de client avec un LEFT JOIN et compter commande.id.
```sql
SELECT client_id, COUNT(*) AS nb
FROM commande
GROUP BY client_id;
```

@003
Q: Pourquoi cette requête est-elle refusée par PostgreSQL ?
C: La colonne nom n'est ni dans le GROUP BY ni dans une fonction d'agrégat
W: La fonction COUNT ne peut pas être utilisée avec une clause GROUP BY sur une ville
W: La table client doit être nommée avec un alias pour être regroupée
W: Le GROUP BY doit contenir chacune des colonnes de la table client
E: Pour chaque ville, plusieurs noms sont possibles : PostgreSQL refuse de choisir. On ajoute nom au GROUP BY ou on l'agrège (MIN(nom), STRING_AGG(nom, ', ')). MySQL l'accepte selon son mode, avec un résultat imprévisible.
```sql
SELECT ville, nom, COUNT(*)
FROM client
GROUP BY ville;
```

@004
Q: Associer chaque fonction d'agrégat à ce qu'elle calcule.
P: COUNT(*) => Le nombre de lignes du groupe
P: SUM(montant) => Le total des montants non nuls
P: AVG(montant) => La moyenne des montants non nuls
P: MIN(date_commande) => La date la plus ancienne du groupe
P: COUNT(DISTINCT client_id) => Le nombre de clients différents
E: Les agrégats ignorent les NULL, sauf COUNT(*). AVG sur une colonne avec des NULL ne divise que par les valeurs présentes, ce qui peut surprendre si NULL voulait dire zéro.

W: Une chaîne vide
E: COALESCE renvoie le premier argument non nul. Utile pour un calcul : prix - remise vaut NULL si remise est NULL, alors que prix - COALESCE(remise, 0) donne le prix.

W: 0
W: prix

E: Toute opération arithmétique avec NULL donne NULL. Une contrainte NOT NULL avec une valeur par défaut évite d'avoir à protéger chaque calcul.

@007
Q: Compléter cette requête qui classe les commandes en « petite » ou « grande » selon leur montant.
A: CASE
E: CASE WHEN … THEN … ELSE … END donne une valeur selon des conditions évaluées dans l'ordre. Sans ELSE, les lignes qui ne remplissent aucune condition reçoivent NULL.
```sql
SELECT id,
       ____ WHEN montant >= 500 THEN 'grande' ELSE 'petite' END AS taille
FROM commande;
```

W: Elle renvoie les dix lignes de plus petite clé primaire, triées dans l'ordre croissant
W: Elle renvoie les dix lignes les plus récentes, d'après la date de modification
E: Le moteur rend les lignes dans l'ordre qui l'arrange, selon le plan choisi. Pour « les dix dernières commandes », on écrit ORDER BY date_commande DESC LIMIT 10.

@009

W: Les clients dont le nom finit par Dup

@010

E: DISTINCT supprime les lignes en double du résultat. Un DISTINCT ajouté pour masquer des doublons venus d'une jointure cache souvent une jointure mal écrite.

```sql
SELECT ____ ville FROM client;
```

@012

U: lignes

@013

W: Elle ne modifie que les commandes déjà annulées

@017

W: TRUNCATE supprime la table et sa structure, DELETE ne supprime que les données

W: TRUNCATE s'annule par ROLLBACK, DELETE ne peut pas être annulé une fois lancé
E: TRUNCATE est bien plus rapide sur une grosse table et ne déclenche pas les triggers ligne par ligne. Dans PostgreSQL, il reste annulable dans une transaction ; DROP TABLE supprime la structure.

W: Les commandes qui ont un autre statut que ces deux-là

@019
Q: Quel est le rôle d'un alias de table, comme c dans FROM client c ?
C: Raccourcir les noms et distinguer deux usages d'une même table

W: Donner un nom permanent à la table, visible par les autres requêtes
W: Accélérer la requête en évitant la relecture du nom de la table
E: Les alias deviennent indispensables pour joindre une table à elle-même, comme un employé et son responsable. Préfixer les colonnes (c.nom) évite les ambiguïtés quand deux tables ont une colonne du même nom.

@020

A: LEFT JOIN
E: L'auto-jointure lit la table deux fois sous deux alias. Avec un LEFT JOIN, le directeur, qui n'a pas de responsable, apparaît avec NULL ; une jointure interne l'écarterait.
```sql
SELECT e.nom, r.nom AS responsable
FROM employe e
____ employe r ON r.id = e.responsable_id;
```

@021
Q: Que renvoie cette requête ?
C: Les clients qui ont au moins une commande
W: Les clients qui n'ont pas encore passé de commande
W: Les commandes qui ont un client connu
W: Le nombre de commandes par client
E: EXISTS s'arrête dès qu'une ligne correspond, sans compter toutes les commandes. NOT EXISTS donne les clients sans commande, y compris quand des colonnes contiennent NULL.
```sql
SELECT nom FROM client c
WHERE EXISTS (SELECT 1 FROM commande o WHERE o.client_id = c.id);
```

@022
Q: Pourquoi cette requête ne renvoie-t-elle aucune ligne alors que des clients n'ont pas commandé ?
C: La sous-requête renvoie un NULL, et NOT IN avec un NULL n'est jamais vrai
W: NOT IN ne fonctionne pas avec une sous-requête dans PostgreSQL
W: La sous-requête doit être nommée avec un alias pour être utilisée
W: Les clients sans commande sont exclus par la clé étrangère
E: x NOT IN (1, 2, NULL) vaut inconnu, jamais vrai, dès qu'une commande a un client_id nul. NOT EXISTS ou un LEFT JOIN … WHERE o.id IS NULL donnent le bon résultat.
```sql
SELECT nom FROM client
WHERE id NOT IN (SELECT client_id FROM commande);
```

@026
Q: Remettre dans l'ordre les étapes logiques de l'exécution de cette requête.
O: FROM et JOIN : réunir commande et client
O: WHERE : garder les commandes de 2026
O: GROUP BY : regrouper par ville
O: HAVING : garder les villes de plus de 10 commandes
O: SELECT puis ORDER BY : calculer les colonnes et trier
E: C'est pourquoi un alias défini dans SELECT ne peut pas servir dans WHERE, mais peut servir dans ORDER BY. LIMIT s'applique en tout dernier.
```sql
SELECT cl.ville, COUNT(*) AS nb
FROM commande co JOIN client cl ON cl.id = co.client_id
WHERE co.date_commande >= '2026-01-01'
GROUP BY cl.ville
HAVING COUNT(*) > 10
ORDER BY nb DESC;
```

@027
Q: Pourquoi cette requête est-elle refusée ?
C: L'alias total n'existe pas encore quand WHERE est évalué
W: La fonction SUM ne peut pas recevoir d'alias dans une requête
W: Le mot total est réservé par le langage SQL standard
W: La clause WHERE doit précéder la clause FROM dans la requête
E: Un filtre sur un agrégat se met dans HAVING : HAVING SUM(montant) > 1000. Pour réutiliser un alias dans un filtre, on passe par une sous-requête ou une CTE.
```sql
SELECT client_id, SUM(montant) AS total
FROM commande
WHERE total > 1000
GROUP BY client_id;
```

@028
Q: Une table de 500 000 lignes est filtrée par WHERE à 20 000 lignes, regroupées en 40 villes, dont 12 passent le HAVING. Combien de lignes le résultat contient-il ?
N: 12
U: lignes
E: Chaque groupe donne une ligne : 40 groupes, dont 12 gardés par HAVING. Filtrer tôt dans WHERE réduit le travail du regroupement ; HAVING ne sert qu'aux conditions sur les agrégats.

@029
Q: Compléter cette requête qui nomme un résultat intermédiaire avec une expression de table commune.
A: WITH
E: Une CTE rend une requête complexe lisible étape par étape. Depuis PostgreSQL 12, une CTE non récursive utilisée une fois est intégrée à la requête par l'optimiseur, sans surcoût.
```sql
____ ventes AS (
  SELECT client_id, SUM(montant) AS total
  FROM commande GROUP BY client_id
)
SELECT c.nom, v.total FROM client c JOIN ventes v ON v.client_id = c.id;
```

@030
Q: À quoi sert une CTE récursive (WITH RECURSIVE) ?
C: À parcourir une hiérarchie, comme une nomenclature ou un organigramme, à profondeur variable
W: À répéter une requête jusqu'à ce qu'elle renvoie le même résultat deux fois de suite
W: À appeler une procédure stockée pour chaque ligne d'une table de faits
W: À mettre en cache le résultat d'une requête pour les appels suivants
E: Une partie de départ sélectionne la racine, une partie récursive ajoute les enfants des lignes trouvées, jusqu'à ce qu'il n'y en ait plus. Une condition de profondeur protège d'un cycle dans les données.

@031
Q: Quelle différence entre RANK() et DENSE_RANK() en cas d'égalité ?
C: RANK saute des rangs après une égalité, DENSE_RANK n'en saute pas
W: RANK classe par ordre croissant, DENSE_RANK par ordre décroissant
W: RANK ignore les NULL, DENSE_RANK les place en première position
W: RANK numérote chaque ligne, DENSE_RANK les égalités entre elles
E: Pour les scores 100, 90, 90, 80 : RANK donne 1, 2, 2, 4 ; DENSE_RANK donne 1, 2, 2, 3 ; ROW_NUMBER donne 1, 2, 3, 4, en départageant au hasard sans critère supplémentaire.

@032
Q: Quel rang RANK() donne-t-il au score 80 pour les scores 100, 90, 90, 80 triés par ordre décroissant ?
N: 4
E: Les deux 90 partagent le rang 2 et occupent deux places : le suivant prend le rang 4. Avec DENSE_RANK, il prendrait le rang 3.

@033
Q: Compléter cette requête qui affiche le montant de la commande précédente du même client.
A: LAG
E: LAG lit une ligne précédente dans la fenêtre, LEAD une ligne suivante. On calcule ainsi l'écart entre deux commandes sans auto-jointure.
```sql
SELECT client_id, date_commande, montant,
       ____(montant) OVER (PARTITION BY client_id ORDER BY date_commande) AS precedent
FROM commande;
```

@034
Q: Que calcule cette fonction de fenêtre ?
C: Le cumul des montants de chaque client, commande après commande
W: Le total des montants de chaque client, répété sur chacune de ses lignes
W: Le total général des montants, répété sur chaque ligne du résultat
W: La moyenne glissante des montants sur les trois dernières commandes
E: Avec ORDER BY dans OVER, la fenêtre va par défaut du début de la partition à la ligne courante. Sans ORDER BY, SUM … OVER (PARTITION BY client_id) donne le total du client sur chaque ligne.
```sql
SUM(montant) OVER (PARTITION BY client_id ORDER BY date_commande)
```

@035
Q: Pourquoi une fonction de fenêtre ne réduit-elle pas le nombre de lignes, contrairement à GROUP BY ?

W: Elle ne peut utiliser que les fonctions COUNT et ROW_NUMBER du langage
W: Elle crée une table temporaire avec les lignes en double de la requête
E: On garde le détail tout en ajoutant un total, un rang ou une part : montant / SUM(montant) OVER () donne la part de chaque commande dans le total général.

@036

P: ROW_NUMBER() => Un numéro unique dans la partition

@040

@041

@043

@044

W: Le caractère % est traduit en expression régulière, que l'index ignore

@046

@048

@050
Q: Compléter cette requête de pagination par clé, plus rapide que OFFSET.
A: >
E: On reprend juste après la dernière valeur de la page précédente. Avec un tri sur plusieurs colonnes, on compare des tuples : WHERE (date_commande, id) < ($1, $2).

@069

W: Une seule règle ouvrant tous les ports de 80 à 443

W: Une erreur, ingress ne peut pas être répété

```hcl
    cidr_blocks = ["0.0.0.0/0"]
  }
}
```

C: Les outputs de la configuration réseau, depuis son état distant
W: Le code source de la configuration réseau, depuis Git
W: Les ressources réseau, pour les recréer dans l'application
W: Les variables saisies par l'équipe réseau
E: terraform_remote_state lit les outputs d'un autre état, ici celui du réseau, utilisables comme data.terraform_remote_state.reseau.outputs.vpc_id. Il faut un droit de lecture sur tout l'état distant, avec ses éventuels secrets : beaucoup d'équipes préfèrent publier les valeurs dans un magasin de paramètres.
```hcl
data "terraform_remote_state" "reseau" {
  backend = "s3"
  config = {
    bucket = "acme-terraform-etat"
    key    = "production/reseau.tfstate"
    region = "eu-west-3"
  }
}
```

@091
Q: Que garantit une politique écrite avec OPA ou Sentinel dans un pipeline Terraform ?
C: Qu'un plan contraire aux règles de l'entreprise soit refusé avant apply
W: Que l'infrastructure coûte toujours moins qu'un budget fixé à l'avance
W: Que le code soit formaté selon les conventions de HashiCorp
W: Que toutes les ressources soient créées dans la même région
E: Le plan, exporté en JSON, est évalué par des règles : pas de base publique, étiquettes obligatoires, types d'instance autorisés, région imposée. Un plan non conforme bloque le pipeline. On codifie ainsi des exigences de sécurité ou de coût plutôt que de compter sur la relecture.

@092
Q: Pourquoi les identifiants de l'intégration continue qui lance terraform apply en production doivent-ils être particulièrement protégés ?
C: Ils permettent de modifier ou détruire toute l'infrastructure
W: Ils servent aussi de mot de passe à la console du fournisseur
W: Ils sont publiés dans le plan joint à chaque demande de fusion
W: Ils expirent dès que le pipeline a terminé son travail
E: Le pipeline de production a des droits très larges : qui contrôle ses identifiants contrôle l'infrastructure. On utilise une fédération OIDC limitée à la branche principale, un rôle séparé pour le plan en lecture seule et pour l'apply, et une approbation humaine avant l'apply.

@093
Q: Remettre dans l'ordre le renommage sans recréation d'une ressource déplacée dans un module.
O: Créer le module et y déplacer le bloc resource
O: Ajouter un bloc moved de l'ancienne adresse vers module.x.y
O: Lancer terraform plan et vérifier qu'il n'affiche que des déplacements
O: Appliquer, puis retirer le bloc moved une fois tous les états migrés
E: Sans bloc moved, Terraform verrait une ressource supprimée et une autre créée. Le plan doit annoncer « has moved to » et aucun remplacement. On garde le bloc tant que d'autres environnements ou modules appelants n'ont pas appliqué la migration.

@094
Q: Combien de ressources seront détruites d'après ce résumé de plan ?
N: 2
E: Le résumé « Plan: 3 to add, 1 to change, 2 to destroy » se lit ainsi : trois créations, une modification sur place, deux destructions. Un remplacement compte à la fois dans add et dans destroy. On remonte toujours dans le détail pour savoir lesquelles sont détruites avant d'appliquer.
```
Plan: 3 to add, 1 to change, 2 to destroy.
```

@095
Q: Pourquoi utiliser une collection Ansible avec une version fixée dans requirements.yml ?
C: Pour que chacun installe exactement les mêmes modules
W: Pour que les playbooks s'exécutent sans connexion SSH
W: Pour remplacer l'inventaire par une liste de collections
W: Pour que les rôles soient chiffrés par ansible-vault
E: Les modules comme amazon.aws ou community.general vivent dans des collections installées par ansible-galaxy collection install -r requirements.yml. Fixer leur version évite qu'une mise à jour change le comportement d'un module entre deux exécutions, comme le fichier de verrouillage de Terraform.

@096
Q: Que fait cette commande ?
C: Elle simule site.yml sur web1 et affiche les écarts
W: Elle applique site.yml à tous les serveurs sauf web1
W: Elle supprime web1 de l'inventaire puis lance site.yml
W: Elle applique site.yml à web1 sans vérification ni affichage
E: --limit restreint le play à un hôte ou un groupe ; --check simule ; --diff affiche les lignes qui changeraient dans les fichiers. C'est la bonne manière de vérifier l'effet d'une modification de rôle sur un serveur avant de l'appliquer partout.
```
ansible-playbook -i inventaire.ini site.yml --limit web1 --check --diff
```

@097
Q: Pourquoi préférer une image construite par Packer à un playbook Ansible lancé à chaque démarrage d'instance dans un groupe Auto Scaling ?
C: Les nouvelles instances démarrent vite et toutes identiques
W: Packer installe les logiciels sans aucun accès réseau
W: Ansible ne sait pas configurer des instances cloud
W: Une image ne peut jamais contenir de faille de sécurité
E: Lors d'un pic de charge, chaque minute de configuration au démarrage retarde l'arrivée de capacité, et un dépôt de paquets indisponible peut faire échouer la mise en service. Une image prête démarre en secondes, testée une fois. Ansible peut d'ailleurs servir à construire cette image, appelé par Packer.

@098
Q: Quelle différence entre count = var.actif ? 1 : 0 et une ressource toujours créée ?
C: La ressource n'existe que si actif vaut vrai, sinon elle est supprimée
W: La ressource est créée deux fois quand actif vaut vrai
W: La ressource est créée mais reste arrêtée quand actif vaut faux
W: Terraform refuse les conditions dans count
E: Ce motif rend une ressource facultative : avec 0 exemplaire, elle n'est pas créée, ou elle est détruite si elle existait. On y fait référence avec un index, aws_instance.bastion[0], ou avec one(aws_instance.bastion[*].id) pour obtenir null quand elle est absente.

@099
Q: Une équipe veut qu'Ansible configure des instances qui apparaissent et disparaissent avec l'autoscaling. Quel type d'inventaire convient ?
C: Un inventaire dynamique qui interroge l'API du fournisseur
W: Un fichier INI mis à jour à la main chaque matin
W: Un inventaire vide, Ansible trouve seul les instances
W: La liste des adresses IP écrite dans le playbook
E: Un plugin d'inventaire comme amazon.aws.aws_ec2 ou azure.azcollection.azure_rm interroge l'API au lancement et forme des groupes à partir des étiquettes, par exemple role=web. Plus de liste à maintenir : une instance créée par l'autoscaling est prise en compte au prochain passage.

@100
Q: Pourquoi une revue de plan Terraform doit-elle porter une attention particulière aux changements sur les ressources IAM ?
C: Un droit trop large passe vite inaperçu et ouvre l'accès à tout le compte
W: Les ressources IAM sont les plus chères de la facture du fournisseur
W: Terraform ne peut pas revenir en arrière sur une ressource IAM
W: Les ressources IAM ne s'affichent jamais dans le plan
E: Une ligne comme "Action": "*" ou un principal trop ouvert dans une politique de confiance donne un pouvoir considérable, sans rien changer de visible au fonctionnement. Ces changements méritent une relecture par un second regard et, idéalement, une règle de politique qui refuse les jokers en production.

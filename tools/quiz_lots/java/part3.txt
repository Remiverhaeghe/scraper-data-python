Q: Quelle différence y a-t-il entre ces deux appels ?
C: start lance un nouveau thread, run s'exécute dans le thread courant
W: run lance un nouveau thread, start s'exécute dans le thread courant

E: start crée un nouveau fil d'exécution qui appelle run de son côté ; appeler run directement exécute simplement la méthode dans le thread courant, sans aucun parallélisme. L'inverse est faux. Les deux appels ne sont donc pas équivalents. Attendre la fin d'un thread est le rôle de join.

@067
Q: Pourquoi ce compteur peut-il afficher moins de 2 000 ?
C: compteur++ n'est pas atomique entre les deux threads
W: Les threads ne démarrent jamais en même temps
W: Un int ne peut pas dépasser 1 000 en Java
W: join interrompt les threads avant leur fin
E: compteur++ lit la valeur, l'incrémente puis l'écrit : deux threads peuvent lire la même valeur et perdre un incrément. On corrige avec synchronized, un AtomicInteger ou un LongAdder. Les threads s'exécutent bien en parallèle, c'est le problème. Un int va bien au-delà de 1 000. join attend la fin du thread, il ne l'interrompt pas.
```
static int compteur = 0;

Runnable incrementer = () -> {
    for (int i = 0; i < 1000; i++) {
        compteur++;
    }
};
Thread t1 = new Thread(incrementer);
Thread t2 = new Thread(incrementer);
t1.start(); t2.start();
t1.join(); t2.join();
System.out.println(compteur);
```

Q: Pourquoi utiliser merge sur une ConcurrentHashMap partagée plutôt que get puis put ?
C: merge met à jour la valeur de façon atomique
W: get puis put est interdit sur une ConcurrentHashMap

W: Un dépassement de pile : réduire la récursion

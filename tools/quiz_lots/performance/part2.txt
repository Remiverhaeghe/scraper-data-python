```java
}

long somme_colonnes(int[][] pM) {
    long rTotal = 0;
    for (int j = 0; j < pM[0].length; j++)
        for (int i = 0; i < pM.length; i++) rTotal += pM[i][j];
    return rTotal;
}
```

W: C'est correct dès lors que les trois serveurs ont reçu le même volume de trafic
E: La vraie valeur dépend de la répartition des requêtes ; elle peut être très différente de la moyenne des p99. Les métriques en histogramme (Prometheus histogram et histogram_quantile, HdrHistogram) se fusionnent puis donnent un percentile juste, à la précision des tranches près.

@089
Q: Deux threads incrémentent chacun leur propre compteur, sans verrou ni donnée partagée, et le programme ne passe pourtant pas à l'échelle. Les compteurs sont voisins en mémoire. De quel phénomène s'agit-il ?
C: Le faux partage : les deux compteurs occupent la même ligne de cache, que les cœurs se disputent
W: Un interblocage entre les deux threads
W: Le verrou global de l'interpréteur
W: Une fuite de mémoire dans la pile des threads
E: La cohérence des caches travaille par ligne de 64 octets : chaque écriture invalide la ligne dans l'autre cœur. On espace les compteurs (remplissage, annotation @Contended en Java) ou on accumule localement avant de fusionner, comme le fait LongAdder.

@090
Q: Sur un serveur à deux processeurs physiques, pourquoi un processus peut-il ralentir quand ses threads tournent sur un socket et sa mémoire est allouée sur l'autre ?
C: La mémoire de l'autre socket (NUMA) est plus lente d'accès
W: Les deux processeurs ne partagent pas le même système d'exploitation
W: La mémoire de l'autre socket n'est pas protégée par la correction d'erreurs
W: Le noyau désactive alors le cache L3 partagé entre les cœurs
E: Chaque socket possède sa propre mémoire ; traverser l'interconnexion ajoute de la latence et consomme de la bande passante. numactl --hardware montre la topologie, numastat les accès distants. Bases de données et JVM (-XX:+UseNUMA) savent tenir compte de cette organisation.

@091
Q: Pourquoi certains profileurs Java classiques désignent-ils des méthodes qui ne sont pas les vraies coupables ?
C: Ils n'échantillonnent qu'aux points de sûreté (safepoints)
W: Ils ne mesurent que le temps passé dans le ramasse-miettes de la JVM
W: Ils ignorent les méthodes compilées par le JIT
W: Ils ne fonctionnent qu'en mode interprété
E: Une boucle compilée sans point de sûreté n'apparaît pas, le temps est attribué à la méthode suivante. async-profiler et Java Flight Recorder échantillonnent sans attendre ces points : leurs graphes en flammes sont plus fidèles et coûtent peu en production.

@092
Q: Un service répond lentement alors que son CPU reste à 15 %. Un graphe en flammes classique ne montre rien de notable. Quelle analyse compléter ?
C: Une analyse hors CPU, du temps passé à attendre disque ou verrou
W: Une analyse du code source par un outil de qualité
W: Un nouveau graphe en flammes avec une fréquence d'échantillonnage doublée
W: Un test de charge avec deux fois plus d'utilisateurs
E: Le profil CPU ne voit que le temps passé à calculer. Le temps perdu à attendre se mesure à part : async-profiler en mode wall, offcputime des outils BCC, ou une trace distribuée qui découpe le temps entre appels. Le faible CPU est justement l'indice d'une attente.

@093
Q: Pourquoi ce benchmark JMH renvoie-t-il le résultat du calcul au lieu de l'ignorer ?
C: Sans utilisation du résultat, le JIT peut supprimer le calcul comme code mort et mesurer une boucle vide
W: JMH exige qu'une méthode de benchmark renvoie toujours un entier
W: Le résultat est enregistré dans le rapport final de JMH
W: Le renvoi force le ramasse-miettes à passer après chaque appel
E: Renvoyer la valeur, ou la passer à un Blackhole, empêche cette élimination. Lire les données depuis un champ d'état @State évite aussi qu'une constante soit calculée une fois pour toutes à la compilation. Un benchmark qui donne 0,3 ns par appel mesure souvent du vide.
```java
@State(Scope.Thread)
public class TriBenchmark {
    int[] aDonnees = genererDonnees(10_000);

    @Benchmark
    public int[] trier() {
        int[] vCopie = aDonnees.clone();
        Arrays.sort(vCopie);
        return vCopie;
    }
}
```

@094
Q: Une API interne répond en 2 ms côté serveur, mais le client mesure régulièrement 40 ms sur de petites requêtes. Quelle cause réseau est classique ?
C: Nagle et l'accusé de réception différé ; TCP_NODELAY corrige
W: Une résolution DNS refaite avant chaque petite requête envoyée par le client
W: Une MTU trop grande sur la carte réseau
W: La compression TLS activée par défaut
E: Nagle retient un petit paquet tant que le précédent n'est pas acquitté, et le récepteur retarde son accusé d'environ 40 ms sous Linux. Les deux attentes se bloquent mutuellement. La plupart des clients HTTP et pilotes activent TCP_NODELAY ; un client écrit à la main l'oublie souvent.

@095
Q: Un banc de mesure en intégration continue doit signaler les régressions de performance. Quelle règle évite les fausses alertes ?
C: Comparer à une référence glissante sur plusieurs exécutions et n'alerter qu'au-delà de la variation habituelle
W: Alerter dès qu'une exécution est plus lente que la précédente
W: Mesurer une seule fois par semaine pour réduire le bruit
W: Lancer les mesures sur les agents partagés les plus chargés pour reproduire la production

@096
Q: Cette boucle s'exécute nettement plus vite quand le tableau est trié au préalable, à nombre d'éléments égal. Pourquoi ?
C: Données triées : le branchement devient prévisible pour le processeur
W: Le tri supprime les doublons et réduit d'autant le nombre de tours de boucle
W: Les données triées tiennent dans moins de mémoire
W: Le compilateur saute les éléments inférieurs à 128
E: Le processeur exécute à l'avance la branche qu'il prévoit ; une erreur de prédiction coûte une quinzaine de cycles. Sur des données aléatoires, il se trompe une fois sur deux. Un compilateur peut aussi remplacer le test par une instruction sans branchement ou vectoriser la boucle, ce qui efface l'écart.
```c
for (int i = 0; i < n; i++) {
    if (donnees[i] >= 128) {
        somme += donnees[i];
    }
}
```

@097
Q: Pourquoi une base de données au tas de mémoire très volumineux gagne-t-elle souvent à utiliser les grandes pages (huge pages) ?
C: Moins d'échecs dans le TLB, le cache des traductions d'adresses
W: Les grandes pages sont compressées par le noyau
W: Elles permettent d'adresser plus de mémoire que la quantité physique installée
W: Elles chiffrent la mémoire partagée entre processus
E: Avec des pages de 4 Ko, 64 Go de mémoire représentent seize millions d'entrées ; avec des pages de 2 Mo, trente-deux mille. PostgreSQL (huge_pages), Oracle et la JVM (-XX:+UseLargePages) en tirent parti. Les Transparent Huge Pages automatiques sont en revanche souvent déconseillées pour les bases, à cause de pauses de compactage.

@098
Q: Que fait cette commande bpftrace sur un serveur de production ?
C: Elle compte, par nom de processus, les appels système d'ouverture de fichier, sans modifier les programmes
W: Elle bloque l'ouverture de fichiers par les processus inconnus
W: Elle enregistre le contenu de tous les fichiers ouverts
W: Elle recompile le noyau avec des sondes de débogage
E: eBPF exécute de petits programmes vérifiés dans le noyau, attachés à des points de trace. On obtient une mesure fine (appels, latences, histogrammes) avec un coût faible et sans redémarrer. Le résultat s'affiche à l'arrêt par Ctrl+C ; les outils BCC (biolatency, execsnoop) en offrent des versions prêtes.
```bash
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'
```

@099
Q: 95 % d'un traitement se parallélise parfaitement. Quelle accélération maximale atteindrait-on avec un nombre illimité de cœurs, d'après la loi d'Amdahl ?
N: 20
E: Avec une infinité de cœurs, la partie parallèle tend vers zéro et il reste 1 / 0,05 = 20. Les 5 % séquentiels suffisent à plafonner le gain. En pratique, la synchronisation et les échanges entre cœurs abaissent encore ce plafond : la loi d'Amdahl est une borne optimiste.

@100
Q: Pourquoi cette version NumPy du calcul est-elle des dizaines de fois plus rapide que la boucle Python équivalente ?
C: Une boucle compilée sur un tableau contigu, sans objet Python par valeur
W: NumPy répartit automatiquement chaque opération sur la carte graphique de la machine
W: NumPy met en cache le résultat des appels précédents
W: NumPy arrondit les calculs à la précision simple pour aller plus vite
E: La boucle Python manipule un objet float par valeur, avec vérification de type à chaque opération. NumPy applique l'opération sur des nombres bruts contigus, que le processeur traite par paquets (SIMD). Pour une boucle impossible à vectoriser, Numba ou Cython compilent le code Python.
```python
import numpy as np

vPrix = np.array(pPrix, dtype=np.float64)
vTtc = vPrix * 1.2
vTotal = vTtc[vTtc > 100].sum()
```

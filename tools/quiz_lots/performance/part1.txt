@001
Q: Quelle différence sépare la latence et le débit d'un service ?
C: La latence mesure la durée d'une requête, le débit le nombre de requêtes traitées par seconde
W: Ce sont deux noms de la même mesure, l'un employé côté réseau et l'autre côté serveur
W: La latence se mesure en octets, le débit en millisecondes
W: Le débit concerne le navigateur, la latence la base de données
E: Les deux évoluent souvent en sens inverse sous charge : regrouper les traitements augmente le débit mais allonge l'attente de chaque requête. Un objectif de performance précise les deux, par exemple 500 requêtes par seconde avec un p95 sous 200 ms.

@002
Q: Pourquoi le temps de réponse moyen suffit-il rarement à décrire la performance ressentie ?
C: Il masque les requêtes lentes, que révèlent p95 et p99
W: Il est trop coûteux à calculer sur un serveur de production chargé
W: Il dépend du nombre de cœurs du poste de l'utilisateur
W: La moyenne arrondit les valeurs à la seconde la plus proche
E: Avec 98 réponses à 50 ms et 2 à 5 s, la moyenne vaut environ 150 ms et paraît correcte, alors que deux utilisateurs sur cent attendent cinq secondes. Le p99 indique la valeur sous laquelle se trouvent 99 % des requêtes : c'est lui qui révèle la traîne.

@003
Q: Que signifie un temps de réponse p95 de 300 ms ?
C: 95 % des requêtes répondent en 300 ms ou moins
W: La requête la plus lente a pris 300 ms
W: Le serveur répond en 300 ms dans 5 % des cas
W: La moyenne des 95 dernières requêtes vaut 300 ms
E: Les 5 % restants sont plus lents, sans limite indiquée : seul le maximum ou un percentile plus élevé (p99, p99,9) les décrit. Un percentile ne se moyenne pas entre serveurs ; on le recalcule sur l'ensemble des mesures ou sur un histogramme fusionné.

@007
Q: Pourquoi cette fonction devient-elle très lente quand les deux listes contiennent 100 000 éléments ?
C: Le test « in » sur une liste parcourt la liste à chaque fois, d'où un coût quadratique
W: La fonction append recopie toute la liste à chaque ajout
W: Python limite les boucles à 10 000 tours
W: La compréhension serait plus rapide parce qu'elle s'exécute dans un autre processus
E: Chaque recherche dans une liste coûte O(n), répétée n fois. Convertir la liste en ensemble avec set(pDejaVus) rend chaque recherche O(1) en moyenne : quelques millisecondes au lieu de plusieurs minutes.
```python
def nouveaux(pClients, pDejaVus):
    rNouveaux = []
    for vClient in pClients:
        if vClient not in pDejaVus:
            rNouveaux.append(vClient)
    return rNouveaux
```

E: L'index range les valeurs de date_commande, pas celles de YEAR(date_commande). On réécrit la condition en intervalle : date_commande >= '2026-01-01' AND date_commande < '2027-01-01'. On dit alors que la condition est sargable. Autre solution : un index sur l'expression.
```sql
SELECT * FROM commande WHERE YEAR(date_commande) = 2026;
```

@043
Q: Un index composite est créé sur (client_id, date_commande). Quelle requête ne peut pas en profiter efficacement ?
C: Une requête filtrée sur date_commande seule
W: Une requête filtrée sur client_id seul
W: Une requête filtrée sur client_id et date_commande
W: Une requête filtrée sur client_id et triée par date_commande
E: Comme un annuaire trié par nom puis prénom, l'index est rangé d'abord par client_id. Sans cette première colonne, les dates sont dispersées dans tout l'index. On place en tête la colonne filtrée par égalité, puis celle des intervalles ou du tri.

@044
Q: Qu'apporte un index couvrant à une requête fréquente ?
C: Il contient toutes les colonnes lues : la table n'est pas lue
W: Il couvre toutes les tables de la base en une seule structure
W: Il verrouille la table pendant la lecture pour éviter les conflits
W: Il remplace la clé primaire de la table lors des jointures SQL
E: PostgreSQL l'indique par Index Only Scan, SQL Server ajoute les colonnes par INCLUDE. Le gain est net sur une requête très fréquente ; en contrepartie l'index grossit et ralentit les écritures. C'est aussi une raison d'éviter SELECT * : lire toutes les colonnes oblige à visiter la table.

@045
Q: Remettre dans l'ordre la lecture d'une donnée selon le modèle cache-aside.
O: L'application cherche la clé dans le cache
O: La clé est absente : l'application lit la donnée en base
O: L'application range la donnée dans le cache avec une durée de vie
O: L'application renvoie la donnée ; les lectures suivantes la trouvent dans le cache
E: C'est l'application qui gère le cache, d'où le nom « à côté ». Lors d'une modification, on écrit en base puis on supprime la clé du cache plutôt que de la mettre à jour : la lecture suivante rechargera une valeur fraîche.

@046
Q: Avec un cache-aside, une donnée est modifiée en base mais les utilisateurs voient l'ancienne valeur pendant dix minutes. Quelle est la cause la plus probable ?
C: La clé n'est pas supprimée du cache à la modification
W: La base de données n'a pas validé la transaction
W: Le cache est trop grand pour la mémoire disponible sur le serveur
W: Le navigateur refuse les données venant d'un cache
E: Sans invalidation, la valeur reste servie jusqu'à l'expiration de son TTL. On supprime la clé après l'écriture en base ; un TTL court reste un filet de sécurité pour les cas oubliés. Plus la donnée doit être fraîche, plus ce point demande de soin.

@047
Q: Une clé très demandée expire et des centaines de requêtes recalculent la même valeur en même temps, ce qui sature la base. Comment nomme-t-on ce phénomène ?
C: Une ruée sur le cache (cache stampede)
W: Une injection de cache par un attaquant
W: Un cache froid au démarrage
W: Une éviction LRU
E: Parades possibles : un verrou pour qu'une seule requête recalcule pendant que les autres attendent ou reçoivent l'ancienne valeur, un rafraîchissement anticipé avant l'expiration, des durées de vie légèrement aléatoires pour éviter que beaucoup de clés expirent ensemble.

@048
Q: Un cache répond en 1 ms, la base en 50 ms, et le taux de succès est de 90 %. Quelle est la durée moyenne d'une lecture, en ms, en comptant 1 ms de consultation du cache même en cas d'échec ?
N: 6
U: ms
E: Les succès coûtent 0,9 × 1 = 0,9 ms ; les échecs 0,1 × (1 + 50) = 5,1 ms ; total 6 ms. Passer à 99 % de succès donnerait 0,99 + 0,51 = 1,5 ms : les derniers points de taux de succès comptent beaucoup.

@049
Q: Associer chaque stratégie d'écriture d'un cache à sa description.
P: Cache-aside => L'application lit la base en cas d'absence et remplit le cache
P: Read-through => Le cache va lui-même chercher la donnée absente à la source
P: Write-through => Chaque écriture met à jour le cache et la base ensemble
P: Write-behind => L'écriture en base est différée et regroupée par le cache
E: Write-behind accélère les écritures mais risque de perdre les données non encore recopiées si le cache tombe. Write-through garde cache et base cohérents au prix d'écritures plus lentes. Cache-aside reste le modèle le plus répandu avec Redis.

@050
Q: Quelle durée de vie donner à une ressource dont l'URL contient l'empreinte du contenu, comme app.3f9a2c.js ?
C: Une très longue, avec max-age=31536000, immutable
W: Aucune mise en cache, avec Cache-Control: no-store
W: Une minute, pour que les mises à jour arrivent vite
W: Une durée calculée à partir de la date de création du dépôt
E: Toute modification du fichier change son nom, donc son URL : l'ancienne version peut rester en cache un an sans risque. La page HTML qui référence ces fichiers garde en revanche une durée courte ou no-cache, pour découvrir les nouveaux noms à chaque déploiement.

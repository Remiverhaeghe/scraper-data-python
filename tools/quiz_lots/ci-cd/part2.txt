@057
Q: Dans cet extrait, pourquoi la commande sh est-elle entre apostrophes simples plutôt qu'entre guillemets doubles avec ${JETON} ?
C: Le shell lit la variable : sa valeur n'entre pas dans le script Groovy
W: Groovy refuse les guillemets doubles dans une étape sh
W: Les apostrophes chiffrent la valeur avant l'envoi au registre
W: Les guillemets empêcheraient docker login de lire l'entrée standard
E: Entre guillemets doubles, Groovy remplacerait ${JETON} avant l'exécution : la valeur se retrouverait dans la ligne de commande, visible des autres processus, et Jenkins signale ce cas. Entre apostrophes, seul le shell la lit, depuis son environnement.
```groovy
withCredentials([string(credentialsId: 'registre-ci', variable: 'JETON')]) {
    sh 'echo "$JETON" | docker login -u ci --password-stdin registre.exemple.fr'
}
```

@058
Q: Sans cache, un build dure 9 min, dont 6 min de téléchargement des dépendances. Le cache est valide pour 80 % des builds et sa restauration prend 1 min. Quelle est la durée moyenne d'un build ?
N: 5
U: min
E: Avec cache : 9 - 6 + 1 = 4 min. Moyenne : 0,8 × 4 + 0,2 × 9 = 3,2 + 1,8 = 5 min. Améliorer le taux de réussite du cache rapporte souvent plus que réduire le temps de restauration.

@073

@074

U: min
E: Deux chemins mènent à deploy : build, test-unit, package (3 + 5 + 2 = 10 min) et build, test-api (3 + 8 = 11 min). deploy démarre à 11 min et finit à 15 min. Seul le chemin le plus long, par test-api, vaut la peine d'être raccourci.

test-api     8 min   needs: build
package      2 min   needs: test-unit

@077

@080

@097
Q: Un secret masqué dans les journaux apparaît pourtant après l'étape echo $SECRET | base64. Pourquoi ?
C: Le masquage cherche la valeur exacte, pas sa forme encodée
W: base64 déchiffre le secret avant de l'afficher
W: Le masquage ne s'applique qu'aux jobs de déploiement
W: Le masquage est coupé sur les runners hébergés
E: Le runner remplace dans la sortie les chaînes identiques aux secrets connus. Encodé, découpé ou inversé, le secret n'est plus reconnu. Le masquage protège d'un affichage accidentel, pas d'un script qui veut l'exfiltrer.

@098
Q: Pourquoi un cache de build distant (Bazel, Gradle) exige-t-il des actions hermétiques ?
C: Une entrée non déclarée fausse la clé du cache
W: Le cache distant n'accepte que des fichiers signés par le runner
W: Le cache distant ne marche que sur un runner privé de réseau
W: Le compilateur refuse toute action qui n'est pas hermétique
E: Si une étape lit une variable d'environnement ou un outil installé non déclaré, deux machines calculent la même clé pour deux résultats différents. Le cache partage alors le mauvais résultat avec toute l'équipe.

@099
Q: Associer chaque stratégie de déploiement à son compromis.
P: Blue-green => Bascule immédiate, mais capacité doublée
P: Canary => Risque limité à une part du trafic, mesures indispensables
P: Rolling update => Pas de capacité en plus, versions mélangées un moment
P: Recreate => Très simple, mais service coupé pendant le remplacement
E: Recreate convient à un outil interne qui accepte une coupure ou à une application qui ne supporte pas deux versions en même temps. Les autres demandent une compatibilité entre versions, notamment du schéma de base.

@100
Q: Une équipe livre une fois par mois de gros lots et subit beaucoup d'incidents. Selon les recherches DORA, quel levier essayer d'abord ?
C: Des changements plus petits et plus fréquents, vérifiés par le pipeline
W: Des mises en production plus rares, pour mieux tester chaque version
W: Une phase de recette manuelle de deux semaines avant chaque livraison
W: Un comité d'approbation externe pour valider chaque changement
E: Un petit changement se relit, se teste et se défait facilement ; un incident se rattache vite à sa cause. Les études DORA n'ont trouvé aucun lien entre comité d'approbation externe et stabilité, mais un lien avec des livraisons plus lentes.

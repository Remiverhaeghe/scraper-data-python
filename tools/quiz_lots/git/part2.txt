@051
Q: Quelle différence entre Git Flow et le développement sur tronc (trunk-based) ?
C: Git Flow multiplie les branches longues, le tronc fusionne de petites branches courtes
W: Git Flow se limite aux projets libres, le tronc aux dépôts privés des entreprises
W: Git Flow interdit les étiquettes de version, le tronc les rend obligatoires à chaque fusion
W: Git Flow demande un serveur GitLab, le tronc fonctionne avec GitHub seulement
E: Git Flow (develop, release, hotfix) convient à des versions livrées rarement. Le tronc, avec des branches d'un ou deux jours et des feature flags, réduit les conflits et va avec la livraison continue.

@052
Q: Une branche de fonctionnalité vit depuis trois semaines. Quel risque grandit chaque jour ?
C: Des conflits plus nombreux et plus difficiles au moment de la fusion
W: Une perte des commits de la branche par le nettoyage automatique de Git
W: Un blocage de la branche par le serveur au-delà de trente jours d'activité
W: Une suppression des étiquettes de version posées sur la branche main
E: Plus main avance, plus l'écart à rattraper est grand. On découpe en livraisons plus petites, on fusionne régulièrement main dans la branche, ou on cache le code inachevé derrière un drapeau.

@053
Q: Que fait git merge --abort pendant une fusion en conflit ?
C: Il annule la fusion et revient à l'état d'avant
W: Il garde la version locale pour chaque conflit
W: Il valide la fusion en ignorant les conflits restants
W: Il supprime la branche que l'on tentait de fusionner
E: Utile quand la fusion se révèle plus compliquée que prévu. --abort exige qu'aucune modification non commitée n'ait existé avant la fusion ; de même, git rebase --abort annule un rebase en cours.

@054
Q: Pendant une fusion, que fait git checkout --theirs config.yml ?
C: Il prend la version de la branche fusionnée pour ce fichier en conflit
W: Il prend la version de la branche courante pour ce fichier resté en conflit
W: Il prend la version du dépôt distant pour ce fichier en conflit
W: Il prend la version de l'ancêtre commun pour ce fichier en conflit
E: --ours garde la version de la branche courante. Attention, pendant un rebase les rôles s'inversent : ours désigne la branche sur laquelle on rejoue, theirs le commit en cours de rejeu.

@055
Q: À quoi sert l'option rerere de Git ?
C: À mémoriser la résolution d'un conflit pour la réappliquer quand il revient
W: À relancer automatiquement une fusion qui a échoué à cause d'un conflit de fichiers
W: À refuser les fusions qui produisent plus de dix fichiers en conflit
W: À récupérer les commits perdus lors d'un rebase mal terminé
E: « Reuse recorded resolution » : avec rerere.enabled=true, un conflit déjà résolu lors d'un rebase précédent est corrigé tout seul. Utile pour une branche longue qu'on rebase souvent.

@056
Q: Comment corriger le dernier commit si l'on a oublié d'y ajouter un fichier, avant de pousser ?
C: Ajouter le fichier puis lancer git commit --amend --no-edit
W: Créer un nouveau commit puis supprimer l'ancien avec git revert
W: Lancer git reset --hard HEAD~1 puis recommencer tout le travail
W: Ajouter le fichier puis pousser avec git push --force-with-lease
E: --no-edit garde le message. L'identifiant du commit change : si le commit était déjà poussé, il faudra forcer, ce qui pose problème sur une branche partagée.

@057
Q: Que fait git log main..feature ?
C: Il liste les commits de feature absents de main
W: Il liste les commits de main absents de feature
W: Il liste les commits communs aux deux branches
W: Il liste les fichiers différents entre les deux
E: Les deux points se lisent « accessible depuis feature mais pas depuis main ». Trois points (main...feature) donnent les commits propres à l'une ou l'autre, utile avec --left-right.

@058
Q: Que fait git commit -p, ou git add -p ?
C: Il propose chaque bloc modifié un à un pour choisir lesquels inclure
W: Il prépare un commit pour chaque fichier modifié du répertoire de travail
W: Il pousse le commit vers le serveur dès qu'il est enregistré
W: Il ajoute les fichiers dont le nom suit un motif donné
E: On sépare ainsi un correctif d'une modification de mise en forme faite dans le même fichier. Des commits ciblés se relisent, s'annulent et se reportent beaucoup plus facilement.

@059
Q: Qu'est-ce qu'un sous-module Git ?
C: Un autre dépôt inclus dans un dossier, figé sur un commit précis
W: Une branche secondaire stockée dans un dossier caché du dépôt
W: Une copie d'un dossier du dépôt envoyée vers un autre serveur
W: Un fichier de configuration qui partage des hooks entre plusieurs projets
E: Le dépôt parent ne garde que l'identifiant du commit du sous-module. Après un clone, git submodule update --init --recursive est nécessaire ; oublier de pousser le sous-module casse le dépôt pour les autres.

@060
Q: À quoi sert Git LFS ?
C: À stocker les gros fichiers binaires à part, le dépôt ne gardant qu'un pointeur
W: À compresser l'historique du dépôt pour le rendre plus rapide à cloner
W: À partager le dépôt entre plusieurs serveurs pour répartir la charge
W: À verrouiller les fichiers texte pendant qu'un développeur les modifie
E: Images, vidéos ou modèles de plusieurs centaines de Mo alourdissent chaque clone. Avec LFS, le fichier n'est téléchargé que pour la version extraite ; le serveur doit le prendre en charge, souvent avec un quota.

@062
Q: Que récupère ce clone lancé en intégration continue ?
C: Il ne récupère que le dernier commit, sans l'historique précédent
W: Il ne récupère que le premier niveau de dossiers du dépôt
W: Il ne récupère qu'une branche, mais avec tout son historique
W: Il ne récupère que les fichiers modifiés lors du dernier mois écoulé
E: Utile en intégration continue pour gagner du temps. git log, git blame ou git describe sont alors limités ; git fetch --unshallow récupère le reste si besoin.

@063
Q: Quelle différence entre un clone partiel (--filter=blob:none) et un clone superficiel (--depth) ?
C: Le partiel garde tout l'historique mais télécharge le contenu des fichiers à la demande
W: Le partiel ne récupère qu'une branche, le superficiel l'ensemble des branches
W: Le partiel ne fonctionne qu'avec Git LFS, le superficiel avec tous les serveurs
W: Le partiel supprime les étiquettes, le superficiel les conserve pour les versions publiées
E: Avec un clone partiel, git log reste complet et les fichiers des vieux commits sont récupérés seulement si on les consulte. C'est souvent le meilleur compromis pour un gros dépôt.

@064
Q: Associer chaque objet interne de Git à ce qu'il représente.
P: blob => Le contenu d'un fichier
P: tree => Un dossier : noms, droits et objets qu'il contient
P: commit => Un instantané avec son arbre, ses parents, son auteur et son message
P: tag annoté => Une étiquette signée ou commentée qui désigne un objet
E: Deux fichiers identiques partagent le même blob, même dans des dossiers ou commits différents. Une branche n'est qu'un fichier contenant l'identifiant d'un commit.

@065
Q: Pourquoi deux fichiers identiques dans deux dossiers différents n'occupent-ils qu'une fois la place dans le dépôt ?
C: Git range les contenus par leur empreinte, et deux contenus égaux ont la même
W: Git compare les noms de fichiers et ne garde que le premier de même nom
W: Git compresse les dossiers entiers et supprime les doublons de chaque archive
W: Git stocke les fichiers identiques dans un dossier partagé entre les dépôts
E: Le stockage est adressé par contenu : l'identifiant d'un objet est l'empreinte de son contenu. Renommer un fichier ne crée donc pas de nouveau blob, seulement un nouvel arbre.

@066
Q: Que fait git gc ?
C: Il compresse les objets en paquets et supprime les objets devenus inaccessibles
W: Il supprime les branches locales qui ne sont plus présentes sur le serveur distant
W: Il vérifie l'intégrité des objets et répare ceux qui sont corrompus
W: Il ferme les fichiers ouverts par Git pour libérer le répertoire
E: Git le lance de lui-même de temps en temps. Les objets accessibles depuis le reflog sont gardés tant qu'il n'a pas expiré : c'est ce qui permet de récupérer un commit perdu pendant plusieurs semaines.

@067

W: La liste des commits de la branche main, du plus récent au plus ancien
W: Le contenu des fichiers de la branche main au dernier commit
W: L'adresse du serveur distant associé à la branche main
E: Une branche n'est qu'un pointeur de 41 octets : la créer ou la supprimer est instantané. Après git pack-refs, les références sont regroupées dans .git/packed-refs.

@068

W: Les commits du serveur sont réécrits pour suivre l'ordre des commits locaux
W: Les commits locaux sont regroupés en un seul avant d'être envoyés au serveur distant
W: Les commits de fusion sont supprimés de l'historique entier du dépôt
E: Sans ce réglage, chaque git pull sur une branche qui a divergé ajoute un commit « Merge branch 'main' of … ». pull.ff=only est une autre option : il refuse de fusionner et oblige à choisir.
```text
[pull]
```

@071

@072
Q: Que signifie cette sortie de git describe --tags ?
C: Le commit courant suit de 5 commits l'étiquette v1.4.0, et son identifiant court est 3f2a9c1

@074

@075

W: La liste des fichiers les plus modifiés au cours de l'année écoulée

W: Le temps passé par chaque développeur sur le dépôt pendant l'année

@076

W: Supprimer le dossier .git puis cloner de nouveau le dépôt depuis le serveur

@077

W: Elle compare la taille de deux branches en nombre de fichiers modifiés

@083

W: La branche locale n'a pas été signée avec une clé SSH

@091
